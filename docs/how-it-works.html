Skill làm việc
như thế nào.

Skill chạy theo một quy trình cố định gồm 8 giai đoạn. Mỗi giai đoạn có điều kiện kiểm tra riêng, và trạng thái của mọi test case đều được ghi trong một file todo duy nhất.

  1. ScanHash source tree, chỉ đọc lại file đã đổi
  2. Phạm viChọn file theo chế độ và git diff
  3. Thiết kếChecklist 9 nhóm, ghi vào todo
  4. Evidence gateGrep từng path:line, case không có bằng chứng bị xóa
  5. Viết testTheo convention của project
  6. ChạyRunner thật, output JSON
  7. Xác minhÁnh xạ TC-xxx, đối chiếu số liệu, thử phá test
  8. Báo cáoSố liệu, bug, rủi ro chưa phủ

Nguyên tắc bắt buộc

Sáu nguyên tắc skill luôn tuân thủ

Mọi bước bên dưới đều phải tuân theo các nguyên tắc này.

Không tự bịa test case

Mỗi case cần bằng chứng dạng path:line (hàm, nhánh if, prop, route, selector, endpoint). Trước khi viết test phải Grep xác nhận. Không có bằng chứng thì xóa case.

Không tự cho pass

PASS chỉ được ghi sau khi runner thật chạy và JSON report xác nhận đúng test mang ID đó đã pass. Không suy đoán.

Không làm test pass giả

Cấm sửa source cho test qua, nới assertion, đổi expected cho khớp actual, .skip/.only, tăng timeout tùy tiện, waitForTimeout, nuốt lỗi, update snapshot mù.

Todo là nguồn dữ liệu chính

Mọi case đi qua file todo. Số liệu trong báo cáo phải khớp todo và log của runner.

Kỳ vọng phải có nguồn

Thứ tự: người dùng → PR/issue/commit → spec/OpenAPI/types/docs → test sẵn có → chính code (chỉ khi hành vi rõ ràng là chủ ý). Code trông sai thì không viết test khẳng định sai mà đánh dấu NEEDS-CONFIRM.

Không động vào secret

Không đọc, scan hay Grep .env*, *.pem, *.key, credentials.json… Không in giá trị biến môi trường ra log hay báo cáo. Cần biến thì hỏi tên, hoặc đọc .env.example.

Từng bước

Khi bạn chạy /qa-test-agent, skill làm gì?

  1. 0

    Khởi tạo lần đầu

    Chưa có .qa-agent/config.json thì skill hỏi hai câu rồi lưu lại, lần sau không hỏi nữa.

    • Q1 Git: commit test sinh ra vào repo hay giữ cục bộ. Skill ghi một khối .gitignore theo lựa chọn, không bao giờ ghi trùng.
    • Q2 Playwright: có / không / hỏi mỗi lần, áp dụng cho frontend. Chế độ audit không bao giờ hỏi Q2.
    • Nếu todo lần trước còn case TODO/WRITTEN, skill hỏi bạn muốn tiếp tục hay làm lại.
  2. 1

    Nhận diện project

    Chỉ đọc các file cấu hình có thật (package.json, lockfile, tsconfig, config của vitest/jest/playwright, pyproject.toml, go.mod…) và ghi vào config.project.

    package managerlanguageframeworkrunnerTesting Library · MSWtest layoutpath aliasrouter · store

    Thiếu test runner thì skill gợi ý một cái phù hợp (Vitest cho Vite/Vue, Jest hoặc Vitest cho React) và hỏi trước khi cài.

  3. 2

    Scan và cache source tree

    node .qa-agent/bin/scan.mjs băm từng file và so với lần chạy trước. File không đổi dùng lại summary JSON đã lưu, nên không bị đọc lại.

    • Cache nằm ở .qa-agent/cache/source-tree.json (path → hash) và cache/summaries/*.json.
    • Skill dựa vào staleSummary, không dựa vào changed. Scan cũng báo file bị ảnh hưởng (impacted) và test liên quan (impactedTests).
  4. 3

    Xác định phạm vi

    Chế độPhạm vi
    defaultHợp của: git diff từ lastRunCommit, thay đổi chưa stage, đã stage, file untracked. Bỏ file test.
    liteCả project, ưu tiên route/page, service/API, store, util có rẽ nhánh. Bỏ file thuần hiển thị.
    fullToàn bộ file nguồn.
    • File bị ảnh hưởng chỉ chạy test sẵn có để hồi quy (vitest related, jest --findRelatedTests), không sinh case mới.
    • Skill đọc ý định thay đổi một lần (git log --format=%B, mô tả PR nếu có gh). Đây là nguồn kỳ vọng.
    Phạm vi rỗng thì báo “không có code mới” và dừng.
  5. 4

    Thiết kế test case

    Với mỗi file trong phạm vi, skill áp dụng các kỹ thuật phù hợp và ghi kỹ thuật vào từng case.

    equivalence · boundarydecision table / branchstate transitionerror guessingfrontend: render · userEvent · a11yintegration + mock APIe2e

    Mỗi unit đi qua 9 nhóm. Nhóm nào cũng ra ít nhất 1 case, hoặc ghi N/A (lý do) vào ma trận phủ.

    inputstate & permissionsdependency failuresconcurrencydata integritytime & localesecurityUX & a11yhappy path
    • Ưu tiên: P0 hỏng là chặn người dùng, mất dữ liệu hoặc lỗ hổng bảo mật · P1 chức năng chính · P2 biên, lỗi nhỏ · P3 thẩm mỹ, hiếm gặp.
    • Có gap case cho những guard còn thiếu trong code, và số case không-happy-path phải ≥ số case happy-path.
    - [ ] TC-012 | P1 | unit | equivalence+boundary
  - Target: src/utils/price.ts → formatPrice
  - Evidence: src/utils/price.ts:23-31 (branch `if (amount < 0)` at L25)
  - Data: amount = -1
  - Expected: throw RangeError (source: code L25-26)
  - Test file: src/utils/__tests__/price.test.ts
  - Status: TODO
  6. 5

    Evidence gate

    Trước khi viết bất kỳ test nào, skill Grep xác nhận bằng chứng của từng case còn tồn tại đúng chỗ.

    • Không xác nhận được: xóa khỏi todo và ghi vào mục Dropped kèm lý do.
    • Kỳ vọng không có nguồn: đánh dấu NEEDS-CONFIRM.
    • Test sẵn có đã assert đúng nhánh đó: loại case với lý do “Already covered”.
  7. 6

    Viết test

    Theo đúng layout, tên file và thư viện mock của project; chỉ dùng layout mặc định khi project chưa có. Tên test chứa [TC-xxx] để ánh xạ ngược kết quả. File sinh ra có header và được ghi vào manifest.json. Sau khi viết, case chuyển sang WRITTEN.

    • Frontend với Playwright (nếu bạn đồng ý): khảo sát DOM thật bằng ui-check.mjs, dùng locator theo role, tự xử lý đăng nhập và nhiều viewport.
  8. 7

    Chạy và xác minh

    • Chỉ chạy file test mới sinh bằng runner của project, bật JSON reporter (Vitest, Jest, Playwright, pytest, go test, dotnet test, maven). Log thô lưu ở .qa-agent/logs/<run-id>/.
    • Ánh xạ kết quả về TC bằng [TC-xxx]. Test không xuất hiện trong kết quả là BLOCKED (“did not run”), không phải PASS.
    • Đối chiếu số liệu: số TC PASS trong todo phải bằng số test pass có ID tương ứng. Lệch thì dừng lại tìm nguyên nhân.
    • Hồi quy: chạy test sẵn có liên quan tới file đổi (full chạy cả suite), báo riêng.
    • Test phải biết fail: với mỗi case P0 đã pass, skill tạo bản sao tạm (git worktree), đảo điều kiện hoặc bỏ guard rồi chạy lại. Test vẫn pass nghĩa là vô dụng và phải viết lại assertion. Không bao giờ làm trên source thật.
    • Coverage: đọc các dòng/nhánh còn hở; thêm case chỉ khi qua evidence gate, tối đa một vòng. Chỉ báo coverage khi runner thật sự in ra.

    Phân loại khi test fail

    LoạiÝ nghĩaXử lý
    FAIL-TESTTest sai (import, selector, mock, setup)Sửa tối đa 2 lần, ghi lý do. Vẫn fail thì BLOCKED.
    FAIL-PRODUCTCode sai so với kỳ vọng có nguồnGiữ test, không sửa source, viết bug report (bước tái hiện, expected, actual, path:line). Hỏi bạn có muốn đánh dấu test.fails để CI không vỡ.
    EnvironmentThiếu env, server không lênBLOCKED ngay, không retry.
    FLAKYKết quả không ổn địnhChạy lại tối đa 3 lần. Không nhất quán thì FLAKY, không tính là PASS.
  9. 8

    Báo cáo và tự kiểm

    Skill ghi .qa-agent/reports/<run-id>.md gồm:

    • chế độ, commit, phạm vi (file scan / đọc mới / lấy từ cache)
    • bảng đếm theo trạng thái và độ ưu tiên, ma trận phủ, rủi ro chưa được phủ
    • bug FAIL-PRODUCT, các case BLOCKED/FLAKY/NEEDS-CONFIRM, case bị loại, hồi quy
    • file đã tạo/sửa và lệnh chạy lại toàn bộ test sinh ra
    Tin nhắn cuối cho bạn tối đa 10 dòng: số pass/fail/blocked, bug đáng chú ý, câu hỏi cần trả lời, đường dẫn báo cáo. Sau đó cập nhật lastRunCommit.

Vòng đời case

Các trạng thái của một test case

TODO→WRITTEN→ PASSFAIL-PRODUCTFAIL-TESTFLAKYBLOCKEDNEEDS-CONFIRM

Hai chế độ đặc biệt: repro và audit

repro: chỉ một test fail để tái hiện bug bạn báo, ở tầng rẻ nhất mà vẫn tái hiện được, không sửa source trừ khi bạn yêu cầu. audit: thay các bước 3 đến 7 bằng truy vết source→sink qua 13 nhóm lỗ hổng, xếp Critical đến Info kèm độ tin cậy, che secret, không sửa hay tấn công gì.

An toàn và giới hạn

Khi nào skill dừng lại

Skill không giới hạn số case. Nó chia todo thành các batch (theo feature hoặc file, ưu tiên P0) rồi lặp lại các bước thiết kế, viết, chạy và ghi nhận cho tới khi mọi case có trạng thái cuối. Trạng thái nằm trong todo nên một lần chạy bị gián đoạn vẫn có thể tiếp tục. Các giới hạn bên dưới giúp tránh vòng lặp không kết thúc.

Giới hạn (cho mỗi lần chạy)

  • Tối đa 8 lần gọi runner mỗi batch.
  • Cùng một lỗi sau hai lần sửa liên tiếp: BLOCKED, không thử lần ba.
  • Số PASS không tăng sau 2 vòng sửa: phần còn lại của batch là BLOCKED, chuyển batch kế.
  • Lỗi môi trường: BLOCKED ngay.
  • Kiểm tra mutation: một lần mỗi case.
  • Cứ 3 batch (hoặc khoảng 60 case), skill gửi bạn một dòng tiến độ rồi tiếp tục trừ khi bạn bảo dừng.

STOP-AND-REPORT

Gặp bất kỳ điều nào sau đây, skill dừng hẳn, đặt vấn đề lên đầu báo cáo và báo bạn tối đa 5 dòng:

  • Nghi mất dữ liệu, hoặc lỗ hổng bảo mật Critical/High
  • Thấy secret thật trong source (được che)
  • Muốn tiếp tục phải sửa source hoặc config chung
  • Test sẽ chạm host không phải local hoặc môi trường thật
  • Cần lệnh phá hủy (drop DB, migration thật, xóa file)
  • Worktree có thay đổi không liên quan có thể bị ghi đè
